## 2. IP 信誉站的判读标准

| 站点 | 看什么 | 合格线 |
|---|---|---|
| `ip.net.coffee/claude/` | Claude 专向：出口 IP、Trust Score、IP 属性、风险信号、滥用记录、支持地区 | 出口与总检一致；Trust Score ≥ 80；家庭住宅 IP；风险信号全「未检测到」 |
| `ping0.cc` | 风控值、IP 类型、是否原生 | 风控值 **< 20%**；类型 = 家庭宽带 / ISP；**原生 IP** |
| `ippure.com` | 人机占比、IP 来源属性 | 系数 **0%**；住宅 IP；原生 IP；human 明显高于 bot |
| `iprisk.top` | Scamalytics 欺诈分、IPQuality、黑名单 | 纯净度 **≥ 90/100**；机房票 **0**；黑名单**全清** |

**判读红线**：只要出现「机房 / 数据中心」标签或黑名单命中 → **换节点**，别硬扛。
**唯一可接受扣分**：`新 IP < 3 月` 这类时间分（新租的 IP 必然扣，等自然变老即可）。
**注意**：这些站是**第三方信誉参考**，不等于 Anthropic 官方认证，只是运行态人工验收工具。没有用户明确要求时不主动跑检测、不解读结果。

## 3. 故障决策树

按顺序查，**每一步都有明确命令和期望值**：

### 第 -1 步：是不是宽带链路限包（MTU 黑洞）

**症状**：国内网站正常、走代理的网页全打不开、托盘提示「Mihomo 无法访问 Internet」。先做这一步再查节点，30 秒定性。

```powershell
ping -f -l 1472 8.8.8.8    # 超时 = 链路过不了 1500 字节的包
ping -f -l 1464 8.8.8.8    # 通 = 链路上限约 1492（PPPoE 特征值）
```

| 结果 | 结论 | 处理 |
|---|---|---|
| 1472 通 | 不是 MTU 问题 | 进第 0 步 |
| 1472 超时、1464 通 | 链路变小，路由器/光猫丢大包且不回报错 | 核对下面两处设置 |
| 1472 报「需要拆分」 | 本机 MTU 已小于 1500，是修复后的正常现象 | 进第 0 步 |

| 位置 | 应设值 | 查法 / 改法 |
|---|---|---|
| Clash → 设置 → 虚拟网卡模式 → 最大传输单元 | `1380` | 用户在界面改；现场值见 `clash-verge.yaml` 的 `tun.mtu` |
| Windows 上网网卡（当前 `WLAN`） | `1400` | `netsh interface ipv4 show subinterfaces`；管理员 `netsh interface ipv4 set subinterface "WLAN" mtu=1400 store=persistent` |

- **两处都要设**：mihomo 连节点的包从物理网卡发出，只改 TUN 不保证恢复。
- **换网卡要重设**：插网线或换无线网卡后，新网卡默认 1500。
- **易被重置**：Clash 升级或重置、Windows 网络重置、重装网卡驱动后复查。
- **根治在路由器**：WAN 口 MTU 设 1492 并开 MSS 钳制，家里其他设备也一并修好；路由器和光猫由用户处理。
- **误判陷阱**：节点测速用 `generate_204`（无响应体），在 MTU 黑洞下会假通过；验证要用有响应体的目标。2026-10-05 一次排查因先查订阅和节点，绕了很久。

### 第 0 步：是不是根本没起来

```powershell
# 三端口是否都在监听、是否都属于 verge-mihomo
Get-NetTCPConnection -State Listen |
  Where-Object { $_.LocalPort -in 43865,43866,43867 } |
  ForEach-Object { "port={0} pid={1} proc={2}" -f $_.LocalPort, $_.OwningProcess,
    (Get-Process -Id $_.OwningProcess).ProcessName }
```
期望：三个端口各 1 行，`proc=verge-mihomo`。缺哪个 → 看 `Script.js` 是否被 Verge 正确加载（Verge 界面「订阅 → 全局扩展脚本」是否能预览）。

### 第 1 步：组选没选中

直接看 Verge 界面「代理」页（mihomo API 走命名管道，9097 未监听）。
期望：`ACCOUNT-US` 有**已选中**节点（不是空、不是「-」）。空 → 说明**新订阅的节点没自动选中**，手动选一个。

### 第 2 步：规则在不在、指向对不对

期望（运行时）：
- 规则总数 ≈ 47（会随订阅变，但**第 1 条永远** `InName account-us-socks -> ACCOUNT-US`）
- Claude 域名规则全部指向 `ACCOUNT-US`
- 没有指向订阅自带组名的规则或 DNS 绑定后缀

### 第 3 步：出口一致性

```powershell
# 四个入口必须同一个 IP
curl.exe --max-time 10 -s https://api.ipify.org                                   # TUN 直连
curl.exe --max-time 10 -s --proxy http://127.0.0.1:43865 https://api.ipify.org     # Code
curl.exe --max-time 10 -s --proxy socks5h://127.0.0.1:43866 https://api.ipify.org  # Chrome
curl.exe --max-time 10 -s --proxy http://127.0.0.1:43867 https://api.ipify.org     # Desktop
```
四个不相同 → **不要用 Claude**，先查规则/组。

### 第 4 步：DNS 有没有旁路

- `clash-verge.yaml` 里 `strict-route: true`、`dns-hijack: [any:53, tcp://any:53]`
- 探针 DNS 应返回 Clash fake-IP 段 `198.18.0.0/16`（基线实测 `198.18.0.53`）
- 探针 `absentProxy` 应 `ECONNREFUSED`（43867 不在时**无回退** = 好事）
- **浏览器自带加密 DNS（DoH，走 443）不受 53 劫持**：会按普通流量落兜底规则 → 进美国线路 → 国内域名被解析成海外 IP、直连海外 IP 卡慢（2026-09-28 Edge 实例）。排查：连接表搜 `cloudflare-dns.com` 等端点，`netstat -ano -p udp` 按源端口反查进程；修复：浏览器「安全 DNS」关闭或指向国内 DoH，改完彻底重启浏览器。现场 `Script.js` 已把 `cloudflare-dns.com` / `dns.google` 置为直连兜底

### 第 5 步：Desktop 专项

1. `HKLM\SOFTWARE\Policies\Claude` 的 `egressProxyUrl` **与** `disableAutoUpdates` **必须同层存在**
2. `configLibrary\_meta.json` 的 `appliedId` 指向的文件内容是 `{"egressProxyUrl":"http://127.0.0.1:43867"}`
3. `docs/配置/Claude环境/Desktop防护/应用直连防护状态.json` 里的 8 条 filter 与 `应用过滤目标.json` 的哈希对得上
4. 注意：英文启动器里的 `Assert-GuardEvidence` 是**门禁**，不通过会 `[BLOCK]`

### 第 6 步：升级后必查

Desktop 每次升级都会换目录 `WindowsApps\Claude_<版本>_x64__pzs8sxrjxfjjc`，VS Code 插件升级也会换版本目录；**WFP 的精确 AppID 条件会失效** → 必须走三端更新迁移对应规则（见 [03 SOP-2](03-变更与回滚SOP.md#sop-2-claude-三端更新)）。

## 4. 环境与编码坑（会真实浪费时间的）

| 坑 | 现象 | 解法 |
|---|---|---|
| **必须 pwsh 7** | 用 `powershell.exe` 5.1 跑本项目脚本 → 报大量 `Unexpected token '}'`、中文变乱码 | 脚本是 **UTF-8 无 BOM**，5.1 按 GBK 读。用 `C:\Program Files\PowerShell\7\pwsh.exe`（桌面 `.lnk` 就是这么配的） |
| **5.1 与 7 共存 ≠ 冲突** | 看到 `powershell.exe` / `pwsh.exe` 两个就以为装重了 | 5.1 是系统组件，**不可卸载**；7 是独立安装。脚本一律显式用 `pwsh.exe` 调用。想手工右键跑脚本：`docs/配置/Claude环境/工具/启用-PowerShell7入口.ps1 -Apply`（只写 HKCU，`-Rollback` 撤销） |
| **Claude Code 的 bash 是 Git Bash** | 中文路径不加引号会被拆开；`$` 变量在嵌套引号里被提前展开 | 路径一律加双引号；复杂 PowerShell 写成 `.ps1` 再 `pwsh -File` 执行 |
| **`Invoke-WebRequest` 取不到非 2xx** | 5.1 没有 `-SkipHttpErrorCheck` | 用 `curl.exe` |
| **WFP 实盘 / Verify 需管理员** | `netsh wfp show filters` 报 `0x00000005` = `ERROR_ACCESS_DENIED` | 非提权时只看 `应用直连防护-Verify.json` 的管理员凭证；要重验由用户以管理员跑 `应用直连防护管理.ps1 -Action Verify` |
| **mihomo 命名管道 API** | 9097 未监听；`/proxies`、`/rules` 大响应是 `Transfer-Encoding: chunked` 且**永不 EOF** | 用 `\\.\pipe\verge-mihomo`；边读边探测累积串是否以 `"0\r\n\r\n"` 结尾；`while(Read>0)` / `ReadTimeout` / `BeginRead` 都会**死锁**。小响应是 `Content-Length`，按长度截断，分块体需按 hex 长度手工解码 |
| **检测站按出口 IP 限流** | 短时间内反复访问，`ping0.cc` 返回 Cloudflare Turnstile 挑战页 | 站点行为，不是本机配置问题；隔一会儿再看 |

## 5. 明确的「不是问题」

以下现象看起来像泄漏，**实际是设计预期**，不要误报：

- 探针 `claude-network-probe.exe` 报 `stunUdp4.ok=true` / `directTcp4=connected`
  → 它**不在** WFP 精确规则名单里（只锁 4 个登记过的 `claude.exe`）。
- 探针 DNS 返回 `198.18.0.53`
  → Clash fake-IP 段，**说明 DNS 没旁路**。
- 探针 `absentProxy = ECONNREFUSED`
  → 43867 不在时**无静默回退到直连**，这是期望行为。
- `HKLM\SOFTWARE\WOW6432Node\Policies\Claude` 存在
  → `SOFTWARE\Policies` 不受 WOW64 重定向，这是冗余镜像，无害。
- 静态 `config.yaml` 里 `strict-route: false` 而运行时有 `true`
  → `Script.js` 在运行时覆盖，**以运行时为准**。
- 非管理员跑 Verify 得到 `failed`
  → 未提权，不是规则缺失。真正判据是 `Desktop防护/应用直连防护-Verify.json` 的 `Status=passed` 与 `PackageVersionMatches=true`。
- Clash 规则用 `160.79.104.0/21` 分流、防火墙用 `160.79.104.0/23` 阻断
  → 两件事，不是写错。
